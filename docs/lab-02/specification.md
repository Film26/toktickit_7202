# Lab 2 Sprint Engineering Specification

> Written retroactively against the code already on `dev/full-app`. See **Section 11 — Deviations from the Lab 2 Baseline** before treating this as a compliance checklist: the implementation both exceeds and falls short of the Lab 2 handout in specific, named ways.

## 1. Sprint Goal

Let a Requester describe an IT problem, submit it as a ticket with a system-generated Ticket Number, and track it through to resolution — with the backend enforcing that a Requester can only ever see their own tickets.

## 2. Stakeholder Request Interpretation

IT needs a way for end users to log support requests without emailing the help desk directly. A Requester should be able to pick a category and related system, describe the problem, set how urgent they think it is, and get a trackable ticket number back. They should be able to find that ticket again later, see its status, and attach supporting files. One Requester must never be able to read another Requester's ticket.

## 3. Scope

### Included
- Ticket creation by an authenticated Requester (category, related system, summary, description, requested priority).
- "My Tickets" list, filterable by status.
- Ticket Detail view for the owning Requester (read-only ticket fields, requested-priority change while open, resolution confirm/reject, reopen request).
- Attachment metadata: a Requester (or staff) can record a filename + URL against a ticket they can access.
- Ownership enforcement on every ticket and attachment route.

### Excluded from this document
- IT Staff queue/triage behavior and Administrator screens — implemented in the codebase, but out of scope for *this* document, which covers the Requester-facing slice only. See Section 11.

## 4. Functional Requirements

- FR-01: A Requester can submit a new ticket with categoryId, optional relatedSystemId, summary (1–200 chars), description, and optional requestedPriority.
- FR-02: The backend generates a unique, human-readable ticket number after the row is created.
- FR-03: A Requester can list their own tickets, optionally filtered by status.
- FR-04: A Requester can open one of their own tickets and see full detail; opening a ticket that belongs to another Requester returns 404, not 403 (existence is not revealed).
- FR-05: A Requester can change `requestedPriority` while the ticket is `NEW` or `IN_PROGRESS`.
- FR-06: A Requester can confirm or reject a `RESOLVED` ticket, and request reopening of a `CLOSED` ticket.
- FR-07: A Requester (or staff) can add an attachment record (filename + URL) to a ticket they can access.
- FR-08: A Requester can add a public comment to a ticket they can access.
- FR-09: Active Categories and active Related Systems are retrievable without ownership restriction, for populating the Create Ticket form.

## 5. Business Rules

- BR-01: The official Ticket Number is generated by the backend (`formatTicketNumber`, pattern `TKT-YYYY-NNNNNN`) after the row exists, so it can embed the row's id; it is never client-supplied.
- BR-02: A new ticket begins with `status = NEW` and `requestedPriority = MEDIUM` unless the Requester specifies otherwise.
- BR-03: Authentication is real JWT login (email + bcrypt-hashed password), not a Development Requester selector. See Section 11 — this is an intentional deviation from the Lab 2 baseline, not an oversight.
- BR-04: A ticket is only visible to its `requester`, or to a user whose role is `IT_STAFF` / `ADMINISTRATOR`. A non-owning Requester gets 404 on `GET /api/tickets/:id`.
- BR-05: `requestedPriority` may only be changed by the owning Requester, and only while `status` is `NEW` or `IN_PROGRESS`; otherwise the API returns 409.
- BR-06: `confirm-resolution` / `reject-resolution` are only valid while `status = RESOLVED`; `request-reopen` is only valid while `status = CLOSED`. Any other starting state returns 409.
- BR-07: Categories and Related Systems are soft-active (`isActive` flag); only active rows are returned by the public list endpoints, but existing tickets keep their reference even if the category/system is later deactivated.
- BR-08: Attachments currently store only `filename` (non-empty string) and `url` (must parse as a URL) — there is no file upload, no MIME-type allowlist, no size limit, and no removal capability. This does not satisfy the Lab 2 attachment rules (5 MB cap, JPG/PNG/WEBP/PDF only, soft removal). Flagged as a gap in Section 11, not silently implemented as compliant.
- BR-09: The "My Tickets" list supports a `status` query filter only; there is no search, sort, or pagination parameter in `GET /api/tickets/mine`.

## 6. UI Specification Summary

See [`ui-spec.md`](./ui-spec.md) for full detail. In short: the app uses Bootstrap's default theme (primary blue), not the Zen Green palette the labsheet specifies — this is documented as a gap, not backfilled with invented styling. Screens covered: Login, My Tickets (Requester dashboard), Create Ticket, Ticket Detail (shared component across roles, gated by role checks in-component).

## 7. Data Changes

Prisma models actually in use (`server/prisma/schema.prisma`): `User` (role: REQUESTER/IT_STAFF/ADMINISTRATOR, isActive, mustChangePassword), `Category` (isActive), `RelatedSystem` (isActive), `Ticket` (requesterId, ownerId nullable, categoryId, relatedSystemId nullable, requestedPriority, itPriority nullable, status, resolutionSummary nullable, timestamps), `PublicComment`, `InternalNote`, `ActionTaken`, `Attachment` (filename, url — no size/mimeType/isActive columns). Indexes exist on `Ticket.status`, `Ticket.requesterId`, `Ticket.ownerId`. There is no soft-delete column on `Attachment`, which is why soft removal isn't implemented (BR-08).

## 8. API Contract

Full contract in [`api-spec.md`](./api-spec.md). Summary of the Requester-relevant surface: `POST /api/auth/login`, `GET /api/categories`, `GET /api/related-systems`, `POST /api/tickets`, `GET /api/tickets/mine`, `GET /api/tickets/:id`, `PATCH /api/tickets/:id/priority`, `POST /api/tickets/:id/{confirm-resolution,reject-resolution,request-reopen}`, `POST /api/tickets/:id/comments`, `POST /api/tickets/:id/attachments`.

## 9. Acceptance Criteria

- AC-01: Given valid ticket data, when a Requester submits the Create Ticket form, then one ticket is saved with `status = NEW` and the generated ticket number matches `TKT-YYYY-NNNNNN`.
- AC-02: Given a non-Requester role, when that user calls `POST /api/tickets`, then the request is rejected with 403.
- AC-03: Given Requester B is logged in, when Requester B requests a ticket owned by Requester A, then the response is 404 and no ticket data is returned.
- AC-04: Given the owning Requester, when they open that same ticket, then it returns 200 and `internalNotes` is omitted from the payload.
- AC-05: Given a ticket in `NEW`, when the owning Requester changes `requestedPriority`, then the update succeeds; given the same ticket in `RESOLVED`, the same call returns 409.
- AC-06: Given a `RESOLVED` ticket, when the owning Requester confirms it, then `status` becomes `CLOSED`; when they reject it instead, `status` becomes `REOPENED`.
- AC-07: Given a `CLOSED` ticket, when the owning Requester requests reopening, then `status` becomes `REOPENED`.
- AC-08: Given no `status` query, when a Requester calls `GET /api/tickets/mine`, then only their own tickets are returned, newest first, with no pagination metadata (there is none to return).

## 11. Deviations from the Lab 2 Baseline

The Lab 2 handout describes a Requester-only slice with a temporary Development Requester selector and explicitly excludes authentication, IT Staff workflow, and Administration functions (Section 4.2 of the handout). The code on `dev/full-app` instead implements, ahead of schedule:
- Real JWT authentication with bcrypt password hashing and a forced first-password-change flow (`server/src/controllers/auth.controller.ts`, `client/src/pages/FirstPasswordChangePage.tsx`).
- Full IT Staff ticket-queue and Administrator (user management, reference-data management) screens (`server/src/routes/users.routes.ts`, `client/src/pages/{ItStaffDashboardPage,UserManagementPage,ReferenceDataManagementPage}.tsx`).
- Public Comments, Internal Notes, and Actions Taken, plus a fuller ticket status workflow (resolve/close/reopen) than the Lab 2 "status stays New" baseline.

Conversely, three things the Lab 2 handout requires are **not yet implemented**:
- Attachment upload with type/size validation, a download endpoint, and soft removal (BR-08).
- My Tickets search, sort, and pagination (BR-09).
- The Zen Green visual theme (Section 6 / `ui-spec.md`).

This document intentionally reports both directions rather than presenting the build as a straight Lab 2 pass. Treat Section 10's "not met" list as the actual remaining backlog if full Lab 2 rubric compliance is the goal.
