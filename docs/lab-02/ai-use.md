## My Reflection

*(Starter draft — replace with your own words before submission; this is Claude's summary of the session, not a substitute for a personal reflection.)*

Using an AI agent to write Lab 2's documentation *after* the code already existed, on a branch that had moved well past Lab 2's intended scope, surfaced a real risk: it would have been easy to ask for "Lab 2 compliance docs" and get back documents that quietly claimed things were done when they weren't (attachment validation, My Tickets search, the Zen Green theme, two untested endpoints). The useful check was making the agent read the actual controllers, schema, and test files rather than paraphrasing the handout, and requiring it to flag every place the code diverged from the spec instead of writing around the gaps.

That paid off directly: once the gaps were named, we went back and actually closed four of them (PRs #29-#32) instead of leaving the documentation as the only deliverable. The most useful moment in the whole session was a mistake, not a success — the agent's own tests.md initially claimed there were zero client-side UI tests, which was wrong (a bad glob pattern), and separately a real bug (removed attachments showing "Removed by unknown") only surfaced because the agent insisted on driving the feature in an actual browser instead of trusting the unit tests alone. Both were caught and corrected in the same session, but only because verification was built into the process rather than assumed. The final documents and code are only as trustworthy as that verification step — I still read and decide on every PR myself before merging.
